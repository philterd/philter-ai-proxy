# Changelog

All notable changes to this project will be documented in this file.

## [Unreleased]

### Security

- **Path traversal scope-bypass closed.** The proxy now rejects any inbound request whose path is not already in canonical form (`path.Clean(p) != p`) with `400` and the new structured code `invalid_request/path_not_canonical`. Without this gate, a per-key `scopes.paths: ["/v1/chat/"]` allow-list accepted `/v1/chat/../v1/embeddings/x` (the HasPrefix scope check passed), and Upstreams that normalize the path before routing then served the request from `/v1/embeddings/x` -- a real scope bypass. The check runs after the early route table (`/livez`, `/readyz`, `/admin/usage`, etc., which use exact-equality matching and are unaffected). Real LLM clients construct canonical paths, so this is expected to be invisible in practice.
- **Bounded `model` Prometheus label cardinality.** The `philter_proxy_prompt_tokens_total{provider, model}` and `philter_proxy_completion_tokens_total{provider, model}` counters use the client-supplied `model` field as a label, which had unbounded cardinality: a holder of any valid API key could exhaust the scraper's memory by issuing one request per random model string. The label is now reduced through a per-provider set capped at 64 distinct values; once full, additional unseen models collapse to `model="other"`. Recognized production model identifiers (typically <20 per provider) are unaffected.
- **Auth lookup is now constant-time.** `keyStore.lookup` previously broke out of its scan loop on the first matching entry, so the elapsed time leaked the position of the matching key -- trivially observable from the network in bcrypt-configured deployments where each entry costs milliseconds. The loop now walks **every** entry regardless of an early match, accumulating into an opaque index that is returned only after the loop completes. Closes the position-oracle. SHA256 configs (the default) add ~1 µs per configured key; bcrypt configs add the per-entry bcrypt cost × N -- continue to use `cost=4` for high-QPS bcrypt deployments as already documented.
- **X-Forwarded-For is no longer trusted by default.** The proxy previously honored `X-Forwarded-For` unconditionally, letting any client spoof their source IP and evade per-IP rate limits or pollute audit logs. The header is now consulted only when the immediate TCP peer (`r.RemoteAddr`) falls inside a CIDR listed in `listen.trustedProxies`. **Behavioral change for deployments behind a load balancer:** add the LB's source CIDR(s) to `listen.trustedProxies` to restore accurate per-IP attribution; deployments without that block now see the LB IP as the client. See [Trusted Proxies / X-Forwarded-For](docs/docs/configuration.md#trusted-proxies--x-forwarded-for).
- **Outbound HTTP clients no longer follow redirects.** All provider clients (Philter, OpenAI, Anthropic, Gemini, Ollama, Azure, Vertex, Bedrock, and `openaiCompatible` entries) now set `CheckRedirect = http.ErrUseLastResponse`. A compromised or DNS-hijacked upstream returning a 3xx with a different `Location` host can no longer cause the proxy to re-send the request -- including its `Authorization: Bearer ...`, `api-key`, and SigV4-signed headers -- to the redirect target. LLM APIs don't use redirects, so this is a pure security hardening with no functional impact.
- **Admin token is now hashed at rest.** Previously stored as plaintext in `cfg.Admin.Token` for the lifetime of the process, the admin token is now SHA256-hashed at startup; the plaintext config field is zeroed immediately after. Comparison is constant-time over the 32-byte hash, which also closes the prior length-leak on `subtle.ConstantTimeCompare` of unequal-length inputs. Brings the admin token to parity with the API-key hashing-at-rest already in place.
- **Generic client error messages for JSON parse / marshal failures.** Paths that previously echoed `err.Error()` (e.g. `bad_json`, `marshal_failed`, `body_read`) now return a fixed, non-revealing message to the client; the full parser detail is logged server-side via slog and correlated by `request_id`. Removes a low-impact information-disclosure surface where parser error strings could leak struct field names or fingerprint version differences.
- **Query-string log sanitizer is now allow-list based.** `sanitizeQuery` (used for any URL the proxy puts into operator-facing logs) previously redacted only `key`, `token`, `api_key`. It now redacts **every** parameter not in a small allow-list of well-known routing/versioning knobs (`api-version`, `alt`, `format`, `prettyPrint`). Unparseable query strings reduce to literal `REDACTED` rather than being echoed raw. Eliminates the risk that a future provider's credential-carrying query parameter (or one accidentally added by a misbehaving client) lands in a log line.
- **`X-Request-Id` is bounded and validated.** An inbound `X-Request-Id` is honored only when it is at most 128 characters and contains only printable ASCII; otherwise the proxy generates a fresh UUID. Closes a memory-amplification surface (large inbound IDs flowing into unbounded audit-log fields) and rules out log-injection via embedded CR/LF.
- **`/admin/usage` per-IP rate limit.** A dedicated in-memory token bucket (5 req/s, burst 10, keyed by client IP) gates the admin endpoint independently of the main request-path limiter (which the admin route bypasses). Exceeding it returns `429` with `Retry-After` and the new structured code `rate_limit_error/admin_rate_limited`. Brute-forcing the admin token is now bounded per-source-IP without affecting other peers.
- **Explicit `tls.Config.MinVersion: TLS 1.2`** on every `tls.Config` the proxy constructs (main TLS listener, mTLS path, provider transports via `buildTLSConfig`, Bedrock client, Redis client). Go 1.25 already defaults to TLS 1.2; making this explicit closes a routine compliance-audit finding and survives any future stdlib default change.
- **`X-Philter-*` headers are no longer forwarded to LLM providers.** The outbound copy loops now drop any header in the `X-Philter-` namespace (the proxy's auth key, policy hints, admin token, etc.) in addition to hop-by-hop headers. Prevents information disclosure of the proxy's internal routing decisions to upstream providers.
- **`auth.apiKeys[].id` (explicit stable identifier).** Each API key may now declare an explicit `id:` (e.g. `team-a`, `billing-reader`) that is used as its stable opaque identifier for rate limits, concurrency, quotas, response-cache tenant prefix, usage export, and audit log `key_id`. **Strongly recommended:** the legacy positional `key-N` fallback is fragile -- inserting or reordering `apiKeys` entries re-shuffles which key owns which historical state, which is a real cross-tenant data leak when the response cache is enabled. Explicit IDs must be unique and may not use the reserved `key-` prefix. Backwards-compatible: entries without `id:` continue to receive the positional identifier. See [Per-key Stable Identifiers](docs/docs/configuration.md#per-key-stable-identifiers).

### Changed

- API keys are now hashed at rest and never held in memory as plaintext. Configured `auth.apiKeys[].key` values accept three formats: plaintext (hashed with SHA256 at load), `sha256$<64-hex>` (pre-hashed), or `bcrypt$<bcrypt-hash>` (pre-hashed). Lookup uses constant-time comparison. Per-key features (rate-limit, concurrency) now key by an opaque stable identifier (`key-N`) so the raw key value never reaches downstream subsystems or log lines. See [API Key Hashing](docs/docs/configuration.md#api-key-hashing) for format reference, the per-format latency table, and CLI recipes for generating pre-hashed values.
- **Structured JSON error responses with stable error codes.** Every error the proxy generates now uses the shape `{"error":{"message":"...","type":"...","code":"...","request_id":"..."}}` with `Content-Type: application/json`. Previously some paths used plain-text `http.Error`. The `(type, code)` pair is a stable public-API enum: existing codes will not be removed or repurposed across minor versions. New codes added since the initial structured-error rollout: `provider_error/{unreachable,response_read_failed}`, `philter_error/request_failed`, `circuit_open/philter_unavailable`, `not_found/bedrock_disabled`. Sub-codes added to existing types: `invalid_request/{bad_json,body_read}`, `unauthorized/{missing_api_key,invalid_api_key}`, `pii_blocked/outbound_blocked`, `rate_limit_error/rate_limited`, `capacity/concurrency_exceeded`, `internal_error/{marshal_failed,request_creation_failed,bedrock_sign_failed}`. See [Error Responses](docs/docs/configuration.md#error-responses) for the full table.
- Every response (success and error) now carries an `X-Request-Id` header. An inbound `X-Request-Id` is honored when present; otherwise a UUID is generated. The same value appears in `error.request_id` (on errors) and `audit.request_id` (on every logged request).
- Audit log entries gain `error_type` and `error_code` fields that mirror what the client received, enabling end-to-end correlation by `request_id`. Audit emission moved into a single deferred call so auth, rate-limit, and concurrency rejections also produce audit entries - previously these paths returned without logging.

### Added

- `--validate-config` CLI flag. Running `philter-ai-proxy --validate-config --config <path>` (or with `PHILTER_PROXY_CONFIG` set) loads the file, expands all `${ENV_VAR}` and `file:` secret references, and runs the same schema validation the proxy applies at startup, then exits without binding any port. Exit `0` prints `config OK: <path>` to stdout; exit `1` prints `config invalid: <reason>` to stderr with the offending field named; exit `2` is reserved for unknown CLI flags. Intended as a CI gate to fail bad configs before they reach a running cluster. CLI parsing now uses the standard `flag` package, so unknown flags are rejected rather than silently ignored. See [Validating a config file](docs/docs/installation.md#validating-a-config-file).
- Per-key `scopes.models` now works for providers that carry the model in the URL rather than the request body (Vertex, Bedrock). Previously the scope check read `extractModel(body)` and saw an empty string for these providers, so a configured `models` allow-list would deny every request from a Vertex or Bedrock key. A new internal `modelForScopeCheck` helper consults `vertexModelFromPath` / `bedrockModelFromPath` first and falls back to the body for other providers. No config change required; existing Vertex/Bedrock keys with model allow-lists begin working immediately.
- First-class **Vertex AI** provider (Gemini on Google Cloud). Enable by setting `providers.vertex.project` and `providers.vertex.location`; the proxy routes Vertex's resource-style paths (`/v1/projects/{project}/locations/{location}/publishers/google/models/{model}:generateContent` and `:streamGenerateContent`), targets `https://{location}-aiplatform.googleapis.com` by default (overridable via `providers.vertex.endpoint`), and authenticates by acquiring a Google OAuth2 access token via [Application Default Credentials](https://cloud.google.com/docs/authentication/application-default-credentials) (workload identity, service account, metadata server, gcloud) — cached and refreshed automatically. Request and response bodies are the Gemini schema, so inbound redaction, outbound scanning, and streaming behavior reuse the existing Gemini path verbatim. The URL-level `{model}` is recorded in the audit log's `model` field (`provider: vertex`). New error codes: `not_found/vertex_disabled`, `provider_error/vertex_auth_failed`. See [providers.vertex](docs/docs/configuration.md#providersvertex).
- **Fine-grained per-key authorization (RBAC).** `auth.apiKeys[].scopes` lets each API key restrict the providers, models, and request paths it may use; unset or empty is full access (backwards compatible). `providers` and `models` accept exact strings or trailing-`*` globs (e.g. `gpt-4*`); `paths` are prefix matches against the request path after any `openaiCompatible[]` provider prefix is stripped. A request must satisfy every non-empty axis (logical AND across axes; OR within each axis). Denials return `HTTP 403` with structured error type `forbidden` and codes `scope_denied_provider`, `scope_denied_model`, or `scope_denied_path`, each mirrored in the audit log alongside the new `key_id` field so denied calls trace end-to-end by `request_id` without ever exposing the raw key. Separately, `auth.apiKeys[].adminRole: usage-read` adds a scoped read-only role that may call `GET /admin/usage` via the regular auth header without requiring the full admin token; the existing all-or-nothing admin token continues to work, and successful exports log `auth_mode` plus the opaque `key_id`. See [Per-key Authorization (scopes)](docs/docs/configuration.md#per-key-authorization-scopes) and [Admin Roles](docs/docs/configuration.md#admin-roles).
- `listen.tlsHandshakeTimeoutMs` bounds how long a client may take to complete the TLS handshake (default 10s). `readHeaderTimeoutMs` only begins ticking after the handshake completes, so a client that opens a TLS connection and dribbles the handshake (or never finishes it) was previously unbounded. Each accepted connection now performs its handshake on its own goroutine under the configured deadline; failed or stalled handshakes are dropped before they reach the HTTP layer and do not stall accepts of other clients. The deadline is cleared on success so post-handshake reads and response streaming remain unbounded. Applies to the main TLS listener; the metrics server, which is HTTP-only, is unaffected. See [Request Hardening](docs/docs/configuration.md#request-hardening).

- Inbound request hardening (`listen`). The proxy now bounds the size and duration of inbound client requests, with secure defaults: `maxRequestBodyBytes` (default 10 MiB; larger bodies are rejected via `http.MaxBytesReader` with `413 payload_too_large` / `request_body_too_large` and the connection closed), `maxHeaderBytes` (default 1 MiB), and `readHeaderTimeoutMs` (default 10s — a slowloris mitigation bounding how long a client may take to send headers). An opt-in `readTimeoutMs` bounds the whole-request read (slow-body attacks) and is disabled by default so large/slow legitimate uploads aren't truncated. No write timeout is set, so streamed responses remain unbounded; the same header limits apply to the metrics server. All limits are tunable and validated (must be ≥ 0). See [Request Hardening](docs/docs/configuration.md#request-hardening).
- Inbound redaction extended beyond chat to the other OpenAI-family JSON endpoints (applies to the OpenAI, Azure OpenAI, and openai-compatible providers): **embeddings** (`input`, string or array of strings; integer token-ID inputs pass through), the **Responses API** (`input` incl. nested message `content[].text`, and `instructions`), **moderations** (`input`), **image generations** (`prompt`), **audio speech / TTS** (`input`), and **legacy completions** (`prompt`). Previously these requests were forwarded without redaction — a PII leak path. The shared OpenAI handler now classifies the endpoint by path suffix and redacts the appropriate field(s) while preserving every other request parameter. Batch/files request bodies (which reference uploaded files rather than inline prompts) and multipart/binary uploads are documented as pass-through. Token-usage accounting now also recognizes the Responses API's `input_tokens`/`output_tokens` and embeddings' prompt-only usage. See the [Redacted Fields](docs/docs/api.md#redacted-fields) table.
- First-class **Azure OpenAI** provider. Enable by setting `providers.azure.target` to your resource endpoint. The proxy routes Azure's deployment-based paths (`/openai/deployments/{deployment}/...`), preserves the `api-version` query parameter (and can inject a configured default when a request omits it), and authenticates either by passing the client's `api-key` header through (default) or, with `providers.azure.entraID: true`, by acquiring an Azure AD / Entra ID bearer token from the default Azure credential chain (managed/workload identity, environment) — cached and refreshed automatically. Inbound redaction and token-usage accounting are identical to the OpenAI provider. New error codes: `not_found/azure_disabled`, `provider_error/azure_auth_failed`. See [providers.azure](docs/docs/configuration.md#providersazure).
- Per-key token quotas, usage export, and an optional response cache for multi-tenant deployments. **Token quotas** (`quota`, off by default) cap cumulative prompt+completion tokens per API key over the current UTC day and month — distinct from rate limits — with a per-key override (`auth.apiKeys[].quota`) and a `quota.default`. A key at/over a window's cap receives `429` with `Retry-After` set to the window reset (type `quota_exceeded`, code `daily_quota_exceeded`/`monthly_quota_exceeded`). **Usage export** via `GET /admin/usage` (`admin`, off by default) returns per-key current-window and lifetime token totals as JSON or CSV (`?format=csv`), protected by a constant-time admin-token check (token accepts `${ENV_VAR}`/`file:` references). **Response cache** (`cache`, off by default) serves repeated non-streaming `POST` prompts from cache — skipping Philter and the provider — keyed on `(key, model, sha256(body))` so tenants never share entries, with `X-Cache: HIT|MISS` headers and a configurable TTL. Quota counters and the cache both support an in-memory backend (default, per-replica) or a shared Redis backend (reusing the rate-limit Redis client) for consistent state across replicas. New metrics: `philter_proxy_cache_hits_total`, `philter_proxy_cache_misses_total`, `philter_proxy_quota_rejections_total{window}`. See [Token Quotas](docs/docs/configuration.md#token-quotas), [Response Cache](docs/docs/configuration.md#response-cache), and [Usage Export](docs/docs/configuration.md#usage-export-admin-api).
- Pluggable rate-limit backend with a shared-state Redis option for multi-replica deployments. The default in-memory backend keeps per-replica token buckets (so N replicas enforce N× the configured limit); setting `rateLimit.backend.type: redis` shares state across all replicas via an atomic server-side Lua token bucket keyed on the Redis server clock, enforcing one consistent limit. Redis connections support TLS (custom CA, optional client-cert mTLS, `insecureSkipVerify` for dev) and authentication (ACL username + password, with the password accepting `${ENV_VAR}` / `file:` secret references). When Redis is unreachable, `rateLimit.backend.failureMode` selects behavior: `open` (default) degrades to the retained local in-memory limiter so traffic keeps flowing, `closed` rejects requests. Backend health is exposed via three Prometheus metrics: `philter_proxy_ratelimit_backend_duration_seconds` (latency, labeled by backend and `ok`/`error`), `philter_proxy_ratelimit_backend_errors_total`, and `philter_proxy_ratelimit_fallback_total`. The memory backend remains the default and is fully backwards-compatible. See [Shared state for multi-replica deployments](docs/docs/configuration.md#shared-state-for-multi-replica-deployments).
- Secret references for API keys. `auth.apiKeys[].key` now accepts `${ENV_VAR}` (read from an environment variable) and `file:/path/to/secret` (read from a file, trailing whitespace trimmed) in addition to literal values, so secrets need not be stored in plaintext in `config.yaml`. References are resolved once at config load — before validation and hashing — so a secret loaded from an env var or file still flows through the SHA256/bcrypt [hashing](docs/docs/configuration.md#api-key-hashing) path. Unset/empty env vars and missing/empty files fail startup with a clear error that names the reference; **resolution and validation errors never echo the secret value**. The resolver is generic and intended to extend to any future secret-bearing field. Includes a documented [key-rotation procedure](docs/docs/configuration.md#rotating-api-keys). Literal keys remain fully backwards-compatible. See [Loading secrets from environment variables and files](docs/docs/configuration.md#loading-secrets-from-environment-variables-and-files).
- k6 load-test harness under `test/load/`. Includes a self-contained docker-compose stack (Philter + stub LLM provider + proxy) and five scenarios: `openai` (inbound redaction), `anthropic` (inbound redaction), `openai-streaming` (SSE pass-through), `outbound-scan` (inbound + outbound Philter redaction), and `no-redaction` (direct-to-stub baseline). A wrapper script (`test/load/run.sh`) runs each scenario via the `grafana/k6` Docker image so no local k6 install is required. A scheduled GitHub Actions workflow runs the harness weekly and on manual trigger, publishing per-scenario summary JSONs as artifacts. Reference baseline numbers (measured on an Intel i5-11400) are published at [Load tests](docs/docs/load-tests.md).
- OpenTelemetry distributed tracing. Set `tracing.enabled: true` to initialise the OTel SDK; configure the OTLP exporter via standard env vars (`OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_PROTOCOL`, etc.). The proxy emits one root span per inbound request (via `otelhttp.NewHandler`) and child spans for each Philter call and each upstream LLM provider call (via `otelhttp.NewTransport`), with `traceparent` automatically propagated to upstreams. The default sampler is `always_off` even after enabling, so no spans flow until the operator opts in via `OTEL_TRACES_SAMPLER`. Audit log entries gain a `trace_id` field when tracing is active and the request was sampled, enabling cross-reference between audit lines and APM traces. With tracing disabled the proxy pays zero per-request tracing overhead. See [Distributed Tracing](docs/docs/monitoring.md#distributed-tracing).
- Split `/health` into Kubernetes-style `/livez` and `/readyz` probe endpoints. `/livez` always returns 200 when the process is up and the listener is accepting connections - it does not probe Philter, so transient upstream outages no longer restart healthy pods. `/readyz` returns 503 only when the Philter circuit breaker is open with `fallback: block` (a state where the proxy will reject every request); in every other state it returns 200. Neither endpoint emits an audit log entry. `/health` is retained for backwards compatibility but is deprecated in favor of the split endpoints. The first-party Helm chart and plain Kubernetes manifests have been updated to point liveness probes at `/livez` and readiness probes at `/readyz`. See [Health Endpoints](docs/docs/monitoring.md#health-endpoints).
- Per-provider HTTP timeouts. Every outbound HTTP client (Philter, each built-in LLM provider, every `openaiCompatible` entry, and Bedrock) now honors a configurable `timeouts:` block with four fields: `connectMs` (default 5000), `tlsHandshakeMs` (default 5000), `responseHeaderMs` (default 30000), `idleConnMs` (default 90000). All four are transport-level, so they bound the network phases without killing streaming responses - once headers are received, the body can stream indefinitely. See [Provider Timeouts](docs/docs/configuration.md#provider-timeouts) for tuning guidance.
- Helm chart, plain Kubernetes manifests, and a starter Grafana dashboard under `deploy/`. The chart at `deploy/helm/philter-ai-proxy/` supports replicas, autoscaling (HPA), Pod Disruption Budgets, optional Ingress, optional Prometheus Operator `ServiceMonitor`, mTLS, and TLS issuance via either an existing Secret or cert-manager. Plain manifests at `deploy/k8s/` provide a minimal Deployment + Service + Secret for non-Helm users. The Grafana dashboard at `deploy/grafana/philter-ai-proxy.json` covers request rate, latency, error rate, redactions, tokens, active connections, and the new concurrency metrics. Kubernetes quickstart documentation added at `docs/docs/kubernetes.md`.
- Fuzz tests for the four polymorphic request parsers: `FuzzAnthropicRequest` (string-or-array content; tool_result string-or-array), `FuzzOpenAIToolCallArgs` (stringified-JSON tool-call arguments recursed through `redactAny`), `FuzzGeminiRequest` (text and arbitrary `functionResponse` maps), and `FuzzBedrockConverseRequest`. Each target drives `ServeHTTP` end-to-end against in-process Philter and provider mocks and asserts that no panic escapes and a status code is always written. A GitHub Actions workflow runs every target for 60s on each PR; discovered crashes are uploaded as artifacts and the crash file becomes a regression seed.
- Max-concurrent-requests guard. `listen.maxConcurrentRequests` caps the total in-flight requests the proxy will process at once; `auth.apiKeys[].maxConcurrent` adds an optional per-key in-flight cap. When either cap is reached the proxy returns HTTP 503 with `Retry-After: 1` and increments `philter_proxy_concurrency_shed_total{scope}` (scope is `global` or `per_key`). Disabled by default for backwards compatibility.
- Per-client rate limiting with optional global backstop. When `rateLimit.enabled: true`, requests are limited by API key (when auth is enabled) or client IP address. Individual keys can override the default limit via `auth.apiKeys[].rateLimit`. A global backstop (`rateLimit.global`) caps total throughput across all clients. Clients that exceed their limit receive `HTTP 429` with a `Retry-After` header. Rate limiting is disabled by default.
- API key authentication and mTLS support. Authentication is disabled by default. When `auth.apiKeys` is configured, clients must present a valid key in the `x-philter-proxy-key` header (configurable); missing or invalid keys receive HTTP `401`. Each key can be bound to a Philter policy override. When `listen.clientCA` is set, the proxy requires and verifies a client TLS certificate on every connection. Both mechanisms can be used simultaneously.
- Token usage tracking: `prompt_tokens` and `completion_tokens` are extracted from non-streaming provider responses and included in the audit log and as Prometheus counters `philter_proxy_prompt_tokens_total` / `philter_proxy_completion_tokens_total` (labeled by `provider` and `model`). Covers all five providers (OpenAI, Anthropic, Gemini, Ollama, Bedrock) and OpenAI-compatible providers.
- Support for multiple OpenAI-compatible providers (Mistral, Cohere, vLLM, LM Studio, etc.) via `providers.openaiCompatible`. Each entry maps a short name to a target URL; clients send requests to `/{name}/v1/...` and the proxy strips the prefix before forwarding. Full PII redaction and audit logging apply.
- Amazon Bedrock Converse API support (`/model/{modelId}/converse`). The proxy signs requests with AWS Signature Version 4 using the standard AWS credential chain (instance profile, IRSA, env vars). Clients send plain JSON with no AWS credentials required. System prompts and all message content blocks are redacted through Philter before forwarding. Outbound scanning is supported. Enable by setting `providers.bedrock.region` in the config.
- Retry and circuit breaker for the Philter backend. Failed Philter calls are retried with exponential backoff (configurable attempts, initial delay, and max delay). A circuit breaker can be enabled to open after a configurable number of consecutive failures, with `block` (HTTP 503) or `passthrough` (forward unredacted with a warning) fallback.
- Outbound response scanning: LLM responses are optionally scanned through Philter before being returned to the client. Disabled by default; enabled per-route or globally via `outbound.enabled: true` in the config. Configurable `action`: `redact` (replace PII), `block` (return HTTP 403), or `flag` (pass through with a warning log). Streaming responses are passed through unchanged with a warning. Outbound scans reuse the same Philter context and document ID as the inbound request for correlation.

### Security

- Removed hardcoded `InsecureSkipVerify: true` from all outbound HTTP transports. TLS certificate verification is now enabled by default for both Philter backend and LLM provider connections.
- Added `PHILTER_TLS_VERIFY` and `PHILTER_CA_CERT` environment variables to configure TLS for the Philter backend connection (supports custom CA certificates for self-signed certs).
- Added `PROVIDER_TLS_VERIFY` environment variable to configure TLS for LLM provider connections.

### Added

- Prometheus metrics endpoint on a configurable port (`metrics.port`, default `9090`). Metrics: `philter_proxy_requests_total`, `philter_proxy_request_duration_seconds`, `philter_proxy_redaction_duration_seconds`, `philter_proxy_entities_redacted_total`, `philter_proxy_philter_errors_total`, `philter_proxy_upstream_errors_total`, `philter_proxy_active_requests`. All labeled by provider and/or policy. See [Monitoring](http://philterd.github.io/philter-ai-proxy/monitoring/) for PromQL examples and Grafana alerting rules.
- `/health` endpoint now checks Philter backend reachability and returns `{"status":"degraded","philter":"unreachable"}` with HTTP 503 when the backend is unavailable; returns `{"status":"ok","philter":"ok"}` when healthy.
- `Filter` function no longer calls `os.Exit` on failure - errors are propagated to callers and result in a `502` response to the client with `philter_proxy_philter_errors_total` incremented.
- Tool-use and function-calling redaction for all providers. OpenAI `role: tool` message content, OpenAI `tool_calls[].function.arguments` (parsed, redacted, re-serialized), Anthropic `tool_result` content blocks, and Gemini `functionResponse` parts are now all redacted before the request is forwarded. OpenAI `role: system` messages are also explicitly covered.
- YAML configuration file support via `--config` flag or `PHILTER_PROXY_CONFIG` environment variable. Supports per-route policy selection based on request headers, URL path, or model name, and per-provider target URLs. Environment variables still work as overrides. Config is validated at startup with clear error messages.
- Streaming (SSE) support for all four providers (OpenAI, Anthropic, Gemini, Ollama). Response chunks are forwarded to the client in real time without buffering.
- Structured audit logging (JSONL) for every proxy request, including request ID, provider, model, policy name, document ID, fields redacted, entity count, entity types detected, redaction latency, client IP, and HTTP status. Enabled by default.
- Added `PHILTER_LOGGING_ENABLED` environment variable (default: `true`) to control audit logging.
- Added `PHILTER_LOG_FILE` environment variable to write audit logs to a file in addition to stdout.
- All proxy output (audit entries, startup, shutdown, errors) is now structured JSON via `log/slog`.

### Changed

- **Configuration file is now required.** Environment-variable-only configuration has been removed. All settings are in the YAML config file, specified via `--config` flag or `PHILTER_PROXY_CONFIG` environment variable.
- Logging and shutdown timeout settings moved into the config file (`logging` and `listen.shutdownTimeout` sections).
- Per-provider TLS clients: each provider now has its own HTTP client with independent `tlsVerify` settings.
- Replaced `httputil.ReverseProxy` with a streaming-capable forwarding function that reads response chunks and flushes them to the client immediately. This enables real-time SSE pass-through for all providers.
- Switched from Philter's `/api/filter` endpoint to `/api/explain` endpoint, which returns entity types and counts in the response. This enables full audit logging of what was redacted.
- Graceful shutdown with connection draining on SIGTERM/SIGINT. In-flight requests are allowed to complete up to a configurable timeout before the process exits.
